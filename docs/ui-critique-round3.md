# UI critique, round 3

This is a source and supplied-image review, not a rendered A/B test. `node_modules` is absent, so I did not run the app in a browser. The supplied `screenshots/image (10).png` is a 668 × 374 reference: a continuous, layered platform scene with characters, small props, foreground framing, multiple depth planes, and controls around the world. It sets an unusually high bar for visual density and apparent agency.

## Highest-impact gap: the answer scene feels like a quiz laid over scenery

`ChallengeView.tsx` puts every challenge inside the same cream `challenge-panel`, then renders a guide, clue, answer controls, hint, and feedback in a vertical stack. In a hunt, `WordHuntScene.tsx` displays three large, isolated SVG objects at fixed normalized coordinates over the same `ForestBackdrop`. Phaser draws only three oval halos and transparent hit zones; it does not render characters, objects, animation, spatial consequences, or a changed world. The `phaser-active` CSS makes the visible HTML buttons ignore pointer input and routes taps through the invisible canvas zones. This does work as multiple choice, but the scene itself does not invite exploration or convey that choosing a word repairs a sign, opens a bridge, or changes anything in the forest. The supplied reference earns its game feel through composition and in-world action; the current core loop earns points while the world remains a backdrop.

This gap will be apparent in the first two tasks (`woods-01` and `woods-02`): the child is told to find an apple or fox, but sees three similarly sized items prominently presented in a row-like triangle. A wrong guess updates a text panel; a correct guess updates text and currency. The chapter story says the sign glows only in the outro, while no sign visibly responds during the challenge. That breaks the design document's promise that understanding English changes a place. The world map has a stronger sense of place than the playable encounter.

**Recommended next slice:** Make the first chapter a specific playable set piece. Place Puck, the signpost, apple, fox, and clue objects in one layered environment; make answer targets visually part of the scene and keep equivalent semantic HTML buttons aligned with them. On success, animate an observable scene change, such as letters returning to the sign and its light turning on, before showing the next control. On a wrong answer, have Puck react and indicate a relevant visual clue. Reuse this scene pattern for later chapters with changed props and spatial layouts. Phaser should own something visible and meaningful if it remains in the interaction path; otherwise the DOM can own the hit targets directly. Do not add invisible canvas hit areas over visible buttons without showing the same hover, focus, and selection feedback for mouse, touch, and keyboard.

## Specific functional and responsive risks

1. **The hunt help ladder is incomplete.** `ChallengeView.tsx` adds the `scaffold` class to correct options after two errors in the generic `answer-scene`, but hunt challenges render through `WordHuntScene.tsx` and never receive that state. The second-error copy says the glowing option will help, yet no hunt object receives the glow. Pass the error/support state into the hunt scene and visibly highlight the correct object, or change that copy for hunts. This is a concrete false promise in the current child-facing flow.
2. **Phaser hit zones can diverge from the artwork as the viewport changes.** `WordHuntScene.tsx` sizes zones from the stage width and height while CSS independently sizes the art buttons to 135 px or 100 px. The canvas overlays the full stage and receives pointer input once active. A tap can therefore select an option outside its visible object, especially on narrow or resized layouts. Use one shared geometry source for visible target and hit target, and verify taps at 320 px, 375 px, and tablet widths.
3. **The mobile shell crowds the activity.** At `max-width:600px`, the six-item main nav persists above every challenge, the quest panel remains nested in the normal page flow, and the hunt scene shrinks to 270 px height. This gives each chapter the feel of a long page beneath a site menu. An active challenge would benefit from an immersive viewport with only a clear back affordance and progress, while the full navigation remains available between encounters. This should be checked in both Hebrew RTL and English LTR with long option text.
4. **Artwork lacks character-specific storytelling.** `App.tsx` uses the same moth portrait for chapter intros and outros except chapter 5's dragon, although the cast includes Puck, Nettle, Hush, Tock, Bramble, and Lyra. `Art.tsx` has a reusable moth, dragon, and three companion SVGs, but no distinct portraits for most speakers. The guide labels change while the visible speaker generally does not. Distinct silhouettes and expressions for the six chapter characters would make dialogue and rewards easier for children to follow.

The current code has meaningful strengths to preserve: large answer controls, a real tap alternative to tile dragging, a separate LTR direction for English clues, bilingual support text, reduced-motion handling, and actual persisted progression. The most useful next review is a real browser pass after dependencies are installed, with screenshots and a complete first-chapter run on narrow English and Hebrew viewports. The source review above does not establish the actual pixel appearance or measured touch behavior.
